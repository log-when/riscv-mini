# DCache 冻结性质 AG 验证全过程复盘与 LLM 自动化经验提取

## 一、过程时间线（实际迭代路径）

1. **目标定义**：`G(!cpu.req.valid) -> FG(!nasti.aw.valid ∧ !ar.valid)` @ DCache
2. **第一轮分解**：直接在 DCache 假设总线公平 → 发现需要 X3-X6 数据契约
3. **arbiter 兑现公平**：无条件公平 `F(aw.ready||ar.ready)` 失败（icache 可永久占用）→ 改条件公平 `F(!valid||ready)` ✓
4. **master 参与假设**：F 形式失败（ready 提前一拍给完就撤）→ X F 失败 → U 形式通过
5. **Cache 兑现参与假设**：遇到拍数错位反例（17 步）→ 加 `readWrap -> r.last` 内部对齐假设
6. **b 通道教训**：`X(b.ready U b.fire)` 失败（b.ready 要等 sWriteAck）→ 弱化 `X F b.fire`
7. **传递层补充**：发现 Cache 端口假设无上游出处 → 建 ArbTransferProp
8. **X4 过度约束发现**：X 前缀禁一拍帧 → 传 assert 时暴露（assume 侧可满足但不可传递）
9. **消融最小化**：逐条删 assume 重跑 + 矛盾断言对照 → 多处冗余删除
10. **工具链探索**：pono IC3 30 分钟 unknown → rIC3 几分钟 safe
11. **性质重构**：`readWrap->last` 引内部信号不可兑现 → ##1 窗口化（PC1/PT-d 成对形式 + 帧形状先验）→ 对齐 priors.json（X4 本就是帧形状，U 形式是多余残留）
12. **对应性审计**：TX5 形式偏差、MUT 缺在案断言 → 修正
13. **无饥饿链延伸**：TX8 FG 失败（自身连续请求）→ F 弱化 ✓
14. **最终**：双侧 rIC3 无界 + priors.json 六条环境叶子，链闭合

## 二、可提取的自动化经验

### 2.1 工作流模式（可编程的循环）

```
目标 → 分解(假设什么) → 反例 → 诊断(缺什么假设/哪条过强) → 修正 → 重跑 → 消融最小化 → 对应性审计 → 升级引擎
```

关键：**每一步只改一个变量**（加一条/删一条/改一个形式），错误归因才可靠。

### 2.2 假设设计规则（性质模式库）

| 规则 | 依据教训 |
|---|---|
| 公平性用条件公平 `F(!valid \|\| ready)`，不用无条件 `F(ready)` | 无条件版被"对方永久占用"击穿 |
| master 参与用 U 形式（保持到完成），不用 F/X F | F 形式留出"提前给完就撤"漏洞 |
| 响应通道（b.ready 类）用 `X F fire`，不用 U | ready 只在末状态成立，U 要求即时 |
| until/frame 用带前提的蕴含：`A -> (!B ##1 (A & B))`，禁止裸序列和 `&` 混排 | 语法分组错误 + SERE 只在蕴含右侧可用 |
| fire 形式 vs valid 形式：约束环境对拍位的承诺用带 fire 的；透传断言与先验**严格同形** | X 前缀过度约束；TX5 形式偏差 |
| 对 DUT 自身输出禁止 assume（自约束） | 写侧帧形状冗余且掩盖 bug |
| 假设只准引用端口信号（环境可见），禁止内部信号 | readWrap 不可被环境兑现 |
| X 前缀慎用：会禁止"上升当拍完成"的一拍帧 | X4 教训 |

### 2.3 反例诊断启发式

- **N 步失败的位置**：浅（<5）= 假设缺失基本约束；深（>15）= 假设间时序错配
- **先查握手拍位**：valid/ready/fire/last 四者的拍位错配是总线性质失败的主因
- **区分"环境未承诺"vs"模块做不到"**：反例里违反的信号由谁驱动，决定修 assume 还是改 assert
- **FG 失败先问"是不是自己造成的"**：TX8 中永久性不成立是因为主体自身连续活动，改 F 前先看前件是否该包含主体停止

### 2.4 消融验证（最小化假设集）—— 应做成标准 pass

- 证毕后逐条删 assume 重跑 BMC；通过=冗余
- **必须做对照**：插入矛盾断言（`X F(!v && v)`）确认检查器真的在工作（防空真）
- 收益：DCache 级 6 条 → 2 条；arbiter 传递级 13 条 → 6 条；发现 X4 残留、写侧帧形状冗余

### 2.5 引擎选择策略

| 场景 | 引擎 | 实测 |
|---|---|---|
| 小模块活性性质 | rIC3（Ic3Check+RIC3） | arbiter 几分钟 safe |
| 含 SRAM 大模块 | rIC3 仍可收敛 | Cache 侧 safe |
| pono 默认 IC3 | 活性 BA 乘积易 unknown | 30 分钟不收敛弃 |
| 迭代调试 | BMC 20（快，出反例波形） | 秒-分钟级 |

策略：**调试用 BMC，定稿升 rIC3**；IC3 超时 30 分钟即切换引擎而不是等待。

### 2.6 对应性审计（跨模块接口检查清单）

1. 公式逐字符同形（连 X 前缀、fire/valid 形式都要一致）
2. 信号同一物理网络（io.dcache ≡ DCache.io.nasti）
3. 每条 assume 必须在某处有同形 assert（悬空检查）
4. 每条 assert 标注依赖：纯先验 / 需 master 参与
5. 与 priors.json 逐条对齐（编号、公式、信号端口）

### 2.7 面向 LLM agent 的具体建议

1. **性质模板库**：§2.2 的规则固化为生成约束，LLM 从模板选形式而不是自由发挥——本过程大部分错误（X 前缀、fire/valid 混用、裸序列）都违反了可枚举的规则
2. **消融 pass 自动化**：decomposer 产出假设集 → 证毕 → 自动逐条消融 → 精简后入库（KB 签名更瘦，匹配率更高）
3. **反例→诊断的分类器**：波形解析提取"违反拍、驱动方、握手拍位错配"三个特征，路由到修 assume/弱化 assert/换形式
4. **弱化顺序枚举**：`U → X F → F`、`FG → F`、`fire → valid` 作为固定的弱化梯度，逐级尝试而不是随机改写
5. **工具链文法检查前置**：`##` 语法（蕴含右侧限定）、SignalName 注册、声明先于引用——这些应在生成后静态 lint，不消耗求解器时间
6. **实例化论证**：同类不同配置（ICache/DCache）不做重复证明，参数代入即覆盖——分解器应识别 RTL 类等价
7. **每轮落盘**：性质编号 + 依赖标注 + 引擎 + 结果进结构化日志，恢复会话/复盘才有据可查
